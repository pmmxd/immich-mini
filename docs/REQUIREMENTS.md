## 2. 项目目标

从 Immich 项目中独立出一个 Windows 本地单用户媒体管理器，项目名为 **Immich Mini**。

核心目标：

- 保留现有 Immich Web 前端的页面、视觉、布局、交互和媒体功能。
- 重新实现更轻量的后端和运行方式。
- 运行时不依赖 Docker、PostgreSQL、Redis 或 WSL。
- 支持本地服务管理工具启动。
- 最终支持项目文件夹内附带的 EXE 启动器。
- 保留人脸检测、人脸聚类和人物命名能力。
- 媒体原文件始终保留在原目录，不复制、不覆盖、不删除。
- 优先降低运行内存，不以牺牲前端功能和媒体能力为代价。

### 3.2 不修改参考项目

- 修改 Docker 配置或运行中的容器。

### 3.3 敏感数据只读

以下内容不得写入、覆盖、迁移或删除：

- Immich 的 PostgreSQL 数据库及其备份。
- 用户照片和视频。
- 已安装程序的 `data` 目录。
- 模型、配置、密码和凭据。

需要接触现有多媒体数据的导入功能，只能通过现有 Immich API 读取，或由用户明确授权后执行。

## 4. 前端复用验收

在新项目中必须能够证明前端未被修改：

1. 保留前端基线路径、提交和聚合哈希。
2. 构建前后运行哈希校验。
3. 新项目前端源码目录与基线文件逐一一致。
4. 允许存在构建产物、依赖目录和后端适配文件，但不能改变前端源码内容。
5. 页面验收必须使用原 Immich 前端的实际页面，不使用新设计的原型页。

禁止行为：

- 用当前 `src/web/App.svelte` 之类的自建页面替代 Immich 前端。
- 只复制截图或样式。
- 只保留时间线而遗漏相册、筛选、地图、人物等现有页面。
- 以“mini 化”为由删减用户可见功能。

## 5. 功能范围

### 5.1 保留功能

- 图片和视频媒体库。
- 全部、图片、视频和横竖屏视图。
- 年月时间线、分页和完整加载。
- 元数据读取和筛选。
- 相册、智能相册、年度相册。
- 标签、收藏、评分、日期、GPS 和城市。
- 地图和位置管理。
- 图片与视频预览。
- 批量选择、创建相册、添加标签、修改 GPS、评分、收藏和删除。
- 人脸检测、人脸聚类、人物命名和人物相册。
- 现有前端的设置、工具和侧边栏页面。

### 5.2 后端简化和移除

- 不建立多用户账号体系。
- 不提供共享链接、合作伙伴或远程用户管理。
- 不运行独立的 Redis 服务。
- 不运行独立的 PostgreSQL 服务。
- 不运行 Docker Desktop。
- 不使用 NestJS、BullMQ 和 OpenTelemetry 作为新后端基础。
- 第一版不实现 CLIP 智能搜索和 OCR，除非用户后续明确批准。

### 5.3 登录冲突处理

当前要求同时包含“不需要登录”和“前端不得修改”。

处理原则：

- 后端不建立真实账号系统。
- 不通过修改前端源码隐藏登录页。
- 可以由后端或启动器提供本地单用户会话兼容层。
- 如果无法在不修改前端的前提下实现无登录体验，必须停止并请用户决定，不得自行改前端。

## 6. 推荐技术架构

### 6.1 后端

- Node.js 22。
- TypeScript。
- Fastify。
- API 和后台任务在同一个 Node 进程中运行。
- 使用限流的任务执行器，避免同时启动大量缩略图和视频任务。

### 6.2 数据库

- SQLite WAL。
- 数据库属于新项目自己的运行数据。
- 不读取或复用 Immich PostgreSQL 文件。
- 核心实体包括资产、相册、标签、人物、人脸、任务和设置。

### 6.3 媒体处理

- Sharp 生成图片缩略图。
- FFmpeg/FFprobe 读取视频信息和生成预览。
- ExifTool 或等效工具提取媒体元数据。
- 原始媒体始终只读。
- 派生文件按内容指纹或路径加修改时间生成。

### 6.4 人脸识别

- Python + ONNX Runtime。
- 使用现有 Immich 人脸模型思路，但作为独立子进程运行。
- 仅在需要扫描或识别时启动。
- 空闲达到阈值后退出并释放模型内存。
- 人脸特征保存在 SQLite。
- 不允许调用云服务，不允许上传用户照片。

### 6.5 前端

- 只使用现有 Immich Web 前端。
- 新项目负责静态托管和 API 兼容。
- 不创建新的设计系统。
- 不引入第二套前端框架。

## 7. API 兼容要求

前端使用的现有 Immich API 协议即为接口合同。

要求：

- 按现有 `@immich/sdk` 和浏览器实际请求实现端点和响应结构。
- 优先实现页面启动、时间线、缩略图、原图、视频、相册、筛选和人物所需接口。
- API 返回格式必须与当前前端一致。
- 不允许要求前端改用新的简化接口。
- 401、403、404、分页、范围请求和错误结构必须与前端预期兼容。
- WebSocket 或实时事件如被现有页面依赖，必须提供兼容实现。

实施 API 前，应先从原前端和现有 SDK 生成端点清单，不得凭印象手写协议。

## 8. 数据模型最低要求

- `assets`：媒体文件、类型、宽高、拍摄时间、元数据、GPS、收藏和评分。
- `albums`：普通、智能和年度相册。
- `album_assets`：相册与资产关系。
- `tags` 和 `asset_tags`：标签关系。
- `people`：人物和名称。
- `faces`：检测框、特征向量和人物关系。
- `jobs`：扫描、缩略图、视频、元数据和人物任务。
- `settings`：媒体目录、界面偏好和运行配置。

SQLite 事务必须保证批量修改的一致性。删除媒体记录不能删除原文件，除非用户通过前端明确执行销毁操作，并且必须先进入回收站。

## 9. 运行和分发

### 9.1 开发运行

- 本机 Node.js 可直接启动后端和前端构建产物。
- 默认只监听 `127.0.0.1`。
- 不使用 Docker、PostgreSQL、Redis、WSL 或后台云服务。

### 9.2 本地服务管理

- 允许通过用户现有本地服务管理工具启动。
- 启动参数、工作目录、日志路径必须明确。
- 不允许依赖终端窗口常驻。

### 9.3 便携文件夹

最终交付结构允许包含：

- `ImmichMini.exe`
- 便携 Node 运行时
- 便携 Python 运行时
- FFmpeg/FFprobe/ExifTool
- 人脸模型
- 后端代码和前端静态文件
- `config`
- `data`
- `logs`

不要求做成单 EXE。所有程序依赖尽量位于项目文件夹内，但 Windows 系统组件或显卡驱动属于系统依赖。

### 9.4 数据目录

- 程序目录和数据目录分离。
- 更新程序时必须保留 `data`、配置、数据库和模型。
- 媒体目录由用户配置，不强制复制到程序目录。
- 不将 SQLite、日志或模型提交到 Git。

## 10. 内存和性能目标

测量必须使用真实构建产物和同一台机器。

| 状态 | 目标 |
|---|---:|
| 后端空闲 | 250–350 MB |
| 正常浏览和轻量任务 | 350–600 MB |
| 批量人脸识别峰值 | 700 MB–1 GB |
| Docker/WSL 运行时依赖 | 0 |

必须记录：

- 启动完成后的 Working Set 和 Private Memory。
- 扫描 1,000 个媒体文件后的占用。
- 打开时间线和预览后的占用。
- 人脸识别峰值及空闲释放结果。

不得只通过删除功能达成指标。若指标无法满足，必须报告实际数据和瓶颈。

## 11. 现有 Immich 数据导入

第一版迁移只通过 Immich API 读取，不直接操作数据库。

需要迁移：

- 资产路径和媒体元数据。
- 相册和相册成员。
- 标签。
- 收藏、评分、日期和 GPS。
- 人物及已命名人脸关系。
- 年度相册。

额外处理：

- 当前智能相册规则有一部分保存在浏览器 localStorage，需要单独导出和导入。
- 导入失败不能影响现有 Immich。
- 导入完成后必须核对数量并生成报告。
- 不删除或修改现有 Immich 数据。

## 12. 安全要求

- 默认只监听 `127.0.0.1`。
- 默认禁止局域网和公网访问。
- 校验 Host 头，降低 DNS rebinding 风险。
- 所有媒体路径必须限制在配置的允许目录内。
- API 不得通过路径穿越读取任意 Windows 文件。
- 日志不得输出密码、令牌或完整隐私元数据。
- EXE 启动器必须防止重复启动和端口冲突。
